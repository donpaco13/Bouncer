Audit Technique Mesures sur Machine Réelle

Audit de Fluidité et Performance — Bouncer

Machine : MacBook Pro Apple M4 (10 cœurs) • macOS 14+ • Configuration multi-écrans avec encoche

Résultat clé : Le coupable n'était pas là où on regardait

La cause n°1 de la sensation d'accroche n'est ni le survol souris, ni le swipe. C'est un usleep(300_000) synchrone sur le MainActor dans ControleurAppsSysteme.masquer(). Chaque bascule entre deux apps régissables fige le thread principal pendant 600 ms (300 ms pour afficher la cible + 300 ms pour masquer l'actuelle), alors que WindowServer propage l'état en 1,5 à 32 ms.

Analyse Détaillée des 5 Suspects

1. Le monitor global .mouseMoved (NotchOverlay.swift)

Constat : Le code antérieur au commit 0797023 appelait effectivement zoneEncoche() (227 µs) et déclenchait SwiftUI des centaines de fois par seconde. Mais le commit 0797023 a déjà mis en cache zoneSensible dans rebuild().

Le calcul d'opacité actuel ne prend plus que 64 nanosecondes quand le curseur est loin. La seule dette résiduelle est système : macOS réveille la runloop de Bouncer pour chaque événement souris sur tout l'écran (~432 000 réveils par heure active).

2. Le timer de refresh() toutes les 2s (WindowManager.swift)

Constat confirmé : Le scan complet scanNotchApps() prend 2,68 ms toutes les 2 secondes (dont 594 µs pour CGWindowListCopyWindowInfo et 490 µs pour résoudre 15 PIDs via NSRunningApplication). En 24h d'inactivité, la machine passe 116 secondes de CPU à scanner des fenêtres inchangées.

De plus, l'assignation lastNotchZoneDescription = "\(ecran) — \(rect)" déclenche inconditionnellement objectWillChange sur WindowManager, forçant SwiftUI à réévaluer le menu toutes les 2 secondes.

Solution : Remplacer le timer par des notifications NSWorkspace.didLaunchApplicationNotification et didTerminateApplicationNotification, et réserver le scan à l'ouverture du menu.

3. Le monitor global .scrollWheel (NotchOverlay.swift)

Constat confirmé : scrollMonitor est installé une fois pour toutes lors du buildPanel(). Dès que l'utilisateur défile sur une page web ou dans son IDE (86 événements par geste), Bouncer intercepte et traite chaque événement sur son thread principal.

Solution : Activer scrollMonitor uniquement quand le curseur s'approche de l'encoche (opacite > 0) et le détacher dès qu'il s'éloigne (opacite == 0). Coût hors encoche : zéro absolu.

4. Redessins SwiftUI et écritures @Published

Constat confirmé : lastNotchZoneDescription n'est utilisé que par le mode CLI --self-test. Son statut @Published provoque une invalidation SwiftUI toutes les 2 secondes. De plus, catalogue.installees() interroge LaunchServices sur disque pour chaque app connue (50 µs) à chaque fois que le corps du menu est évalué.

5. La cause racine du freeze : usleep(300_000)

Dans ControleurAppsSysteme.masquer() (ligne 148) :

public func masquer(_ masquee: Bool, pid: pid_t) -> Bool {
    let appElement = AXUIElementCreateApplication(pid)
    let countBefore = compteFenetres(pid: pid)
    AXUIElementSetAttributeValue(appElement, kAXHiddenAttribute, ...)
    usleep(300_000) // <-- FREEZE DE 300 MS SYNCHRONE SUR LE MAIN THREAD
    let countAfter = compteFenetres(pid: pid)
    return ...
}

Lors d'une bascule : masquer(false, cible) dort 300 ms, puis masquer(true, actuelle) dort 300 ms. Total = 600 ms de gel total de l'application. Or, nous avons mesuré que WindowServer propage le masquage en 1,5 à 32 ms !

Plan d'Action Recommandé

  1. P0 (Immédiat) : Passer masquer() en asynchrone non-bloquant avec sondage court (15 ms) et timeout à 100 ms max. Supprime instantanément les 600 ms de gel UI.
  2. P1 (Immédiat) : N'attacher scrollMonitor que lorsque opacite > 0. Supprime 99,9% des réveils de scroll sur la machine.
  3. P2 (Fond) : Remplacer le timer 2s de refresh() par des notifications NSWorkspace et ne rafraîchir à chaud qu'au clic sur le menu.
  4. P3 (Propreté) : Retirer @Published de lastNotchZoneDescription pour couper les invalidations SwiftUI parasites.
